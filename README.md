# 牌譜工房 — Mahjong Paifu Editor

天鳳 `tenhou.net/6` 系の四人リーチ麻雀JSON牌譜を、正方形の卓画面で再生・編集する完全クライアントサイドWebアプリです。牌の変更を表示だけで済ませず、物理牌の取得元（配牌・ツモ）と後続の打牌・副露参照まで追跡し、4枚制約、手牌枚数、手順、リーチ、和了形、点数連続性を再検証します。

牌譜はブラウザー内でだけ処理します。サーバーへのアップロード、リポジトリへの保存、外部ストレージへの送信は行いません。

## 対応形式

`sample.txt` と同じ17要素の局配列を持つ天鳳 `/6` JSONです。

```text
[
  [局番号, 本場, 供託], 開始点, ドラ表示牌, 裏ドラ表示牌,
  東家配牌, 東家ツモ/副露, 東家打牌/槓,
  南家配牌, 南家ツモ/副露, 南家打牌/槓,
  西家配牌, 西家ツモ/副露, 西家打牌/槓,
  北家配牌, 北家ツモ/副露, 北家打牌/槓,
  局結果
]
```

- 通常牌は `11`〜`47`（萬・筒・索・字牌）、赤5は `51`・`52`・`53`
- 打牌 `60` は直前ツモ牌のツモ切り、`r13`／`r60` はその打牌でのリーチ成立
- `c` はチー、`p` はポン、`m` は大明槓、`a` は暗槓、`k` は加槓
- 副露文字列中のマーカー直後の2桁が鳴いた牌です。ポン・槓ではマーカー位置から相対席も復元します
- `["和了", 点数移動, [和了者, 放銃者], ...]` の複数和了、`["流局", 点数移動]`、天鳳の途中流局名を保持
- 未知のトップレベルフィールドとルールフィールドは往復時に保持

四麻の東風戦・半荘戦、赤牌、リーチ、チー、ポン、大明槓、暗槓、加槓、ロン、ツモ、流局を扱います。三麻や独自形式は四麻として推測せず、入力位置付きのエラーを表示します。

## 使い方

起動すると同梱の `sample.txt` を読み込みます。上部の「JSONを開く」、画面へのドラッグ＆ドロップ、または「貼り付け」から別の牌譜を開けます。

1. 左で局、下のスライダーまたは再生ボタンでイベントを選ぶ
2. 卓上の手牌・河・副露・ドラ表示牌をクリックする
3. 右側の牌パレットや副露・リーチ・開始点操作を選ぶ
4. 編集は補正キューへ入り、計算中も続けて別の牌を編集できる
5. 上部の「変更ログ」で手動変更・自動補正・失敗理由を確認する
6. Undo / Redo、元の牌譜へ戻す、互換JSONのコピーまたはファイル保存、編集プロジェクト保存を行う

互換JSONはコピー用ダイアログを開いてその場でクリップボードへコピーできます。ファイル保存も残しており、対応ブラウザーではOSの保存ダイアログ、それ以外では通常のダウンロードへフォールバックします。一度オンラインで開いたビルドはService Workerによりオフラインで再利用できます。

### 手動変更・自動補正・固定

- **手動変更**: ユーザーが指定した牌、副露、リーチ、点数。青い変更印で表示
- **自動補正**: 4枚制約の玉突き交換、取得元・後続参照、副露後の手順、和了不能時の流局化など。金色の変更印で表示
- **固定**: 牌の取得元または局開始点に対するハード制約。自動補正は上書きしない

固定条件とルール不変条件を同時に満たす解がなければ、編集前の状態を維持して衝突理由を表示します。局開始点を固定した地点は点数伝播の境界となり、その後は固定点を新しい基準として伝播します。

## 自動補正

補正は同じ入力・編集・乱数シードから同じ結果を生成します。候補は次の順で比較します。

1. ユーザー指定と固定値
2. 元の和了者・放銃者・終局種別・点数
3. 元のリーチ・副露
4. 4枚使い切り時は、未リーチ他家の手牌、未リーチ他家の河、非和了リーチ者の河、非和了リーチ者の手牌
5. 自動変更数、編集地点からの距離、公開情報の変更量
6. 牌コード、席、イベント番号による安定したタイブレーク

牌変更は物理牌IDから取得元へ遡り、ツモ切り以外の後続打牌や副露トークンも同じ物理牌として変更します。五枚目が発生した場合は、交換先で別の五枚目が生じない牌種まで玉突きで差し替えます。通常の交換候補は他家の未リーチ手牌・河などを優先し、編集中の自分の手牌同士で見た目が元に戻る交換は最後に回します。指定牌が打牌時の手牌にない場合も取得元を変更するため、「河だけが履歴と食い違う」状態を作りません。

既存のポン・槓に含まれる1枚だけを五枚目解消へ流用することはありません。他に交換候補がない場合は、同じ数字の別スートを優先して副露全体を別牌へ置き換え、さらに周囲の物理牌を玉突き補正して副露の組を保ちます。

副露追加は河牌・相対席・必要牌を確認し、通常ツモを副露に置き換え、直後の打牌、以後の手番、嶺上ツモ、カンドラを再構成します。現在の手牌・河だけでは鳴けない場合は、続行確認後に作りたい牌姿と相手を指定できます。選択巡目に近い未使用打牌と、直近に取得した手牌を自動差し替えしてチー・ポン・各種カンを成立させます。削除では逆に通常手番へ戻します。

卓上では、短くなった手牌を左から並べ、その末尾に少し間隔を空けて副露を続けて表示します。

牌変更や副露によって後続のリーチが門前・聴牌条件を失った場合は、変更自体を拒否せず、そのリーチ宣言と1000点供託を自動解除します。その結果として元の和了が成立しなくなった局は、決定論的に牌山を補完して流局へ変更します。改ざんしたツモで役あり和了が新たに成立した場合は、そのツモ時点で後続手順を止め、役・本場・供託を含むツモ和了へ変更します。和了形を見送った同巡内のロンと、自河に和了牌があるロンは振聴として認めません。

編集により元のロン・ツモ和了形を保てない場合、残りの物理牌を保存済みシードで決定して牌山終了までツモ切りを生成し、最終聴牌者からノーテン罰符を計算して流局化します。変化した点数・供託は後続局へ伝播します。

最初の4打牌が同一の風牌で、副露・暗槓を挟んでいなければ `["四風連打"]` で途中流局にします。カンは1局合計4回までで、1人が4回行った場合だけ局を続行します。2人以上で4回に達した場合は、その後の打牌に合法なロンがなければ `["四槓散了"]`（四槓流れ）で途中流局にし、5回目のカン要求は適用前にエラーにします。

## 編集プロジェクト

拡張子は `.mjpe`、内容はJSONです。互換牌譜JSONとは別に以下を保存します。

- 元JSONと現在の互換JSON
- 手動編集コマンドと全自動変更理由
- Undo / Redo用のトランザクション前後状態
- 固定参照
- 補正優先順位バージョン
- 自動生成用乱数シード
- データ形式バージョンと更新日時

互換JSONへ独自フィールドは追加しません。

## ローカル開発

Node.js 22以降を推奨します。

```bash
npm install
npm run dev
```

表示されたローカルURLをブラウザーで開きます。

```bash
npm run typecheck
npm run lint
npm test
npm run test:stress
npm run build
npm run preview
```

通常テストは `sample.txt` の全局Codec往復・前向き再生、物理牌制約、取得元補正、5枚目交換、副露追加削除、加槓、流局補完、点数伝播、固定境界、Undo / Redo、プロジェクト往復、決定論的ランダム編集、主要GUI操作を含みます。`test:stress` は決定論的編集をより多く繰り返す長時間テストです。

## ビルドとGitHub Pages

Viteの `base` は `./` なので、ユーザー/組織ページとリポジトリ名付きサブパスの両方でアセットURLが壊れません。

1. GitHubで Settings → Pages → Source を **GitHub Actions** にする
2. `main` ブランチへpushする
3. `.github/workflows/deploy-pages.yml` が型検査、lint、テスト、production buildを実行し、`dist` をPagesへ公開する

手動実行はActions画面の「Deploy to GitHub Pages」から `workflow_dispatch` を選びます。

## アーキテクチャ

```text
Codec (元JSONを位置付き診断で読書き)
  ↓
正規化イベント + 物理牌トレース
  ↓
前向き状態機械 ─→ 各イベント後のValidator
  ↓                    ↓
GUI派生状態       制約・得点台帳
  ↓                    ↓
編集要求 ─→ Web Worker補正Solver ─→ 変更理由付きトランザクション
                                      ↓
                         互換Encoder / Project保存
```

- `src/domain/codec.ts`: `/6` 圧縮形式、位置参照、往復
- `src/domain/replay.ts`: イベント列と物理牌状態機械
- `src/domain/validator.ts`: 牌数、手牌、ツモ切り、リーチ、和了形、局間点数
- `src/domain/solver.ts`: ハード制約、交換、手順再構成、流局補完、点数伝播
- `src/domain/project.ts`: トランザクション、Undo / Redo、固定、保存
- `src/components`: 卓、タイムライン、編集インスペクター、変更ログ、JSONコピー

重い補正探索は `solver.worker.ts` へ分離します。編集要求はキューで順番に処理し、GUIには進捗、計算中の牌、反映時の短い強調を表示します。計算中も卓操作を止めません。

## ルール上の仮定

- `rule.disp` の「四」を四麻判定に使い、`aka51`〜`aka53` または `aka` を赤5上限として解釈
- 局番号は東1局を0として、親は `局番号 % 4`
- リーチ文字列は宣言打牌と成立が連続したものとして1000点を台帳へ記帳
- 局結果配列の点数移動は和了・流局の確定台帳。供託受取により合計が0でない和了移動も許容
- 明示されない牌山・王牌は物理牌上限内の未確定スロット。流局延長時だけ決定論的に確定
- 流局罰符は聴牌者1/2/3人でそれぞれ +3000/+1500/+1000、ノーテン者で均等負担
- 途中流局は天鳳の結果名を使い、四槓流れは互換JSON上で `四槓散了` と出力
- 和了見送りは和了役の有無にかかわらず和了形で判定し、非リーチ者は次の自分の打牌、リーチ者は局終了までロン不可
- 天鳳の書式は変更される可能性があるため、未知表現は推測せず入力エラーとする

和了形とシャンテンはエディター内の標準形・七対子・国士無双判定に加え、門前手では `@kobalab/majiang-core` のシャンテン判定をアダプター越しに使用します。役・符・点数・本場・供託を含む和了判定も同ライブラリをアダプター越しに行います。途中編集の部分状態など外部APIが表現できない箇所は内部判定へフォールバックします。
